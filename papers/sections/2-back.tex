This section describes background on embeddings, vector search, similarity joins, and GPU-accelerated data processing.

\subsection{Embeddings and Vectors}\label{subsec:embeddings-and-vectors}

% what embeddings/vectors are, and the metrics that compare them
A vector embedding is a fixed-length array of numbers that a machine learning model produces from a piece of data, such as a passage of text, an image, an audio clip, or a table row.
Modern embedding models produce vectors with hundreds to thousands of dimensions.
The model is trained so that geometric proximity in the embedding space reflects semantic similarity: similar inputs map to nearby vectors, and unrelated inputs map farther apart.
Comparing two objects semantically therefore reduces to computing a distance or similarity score between their vectors, most commonly Euclidean (L2) distance, cosine similarity, or inner product.
All three can be computed from dot products and vector norms (Section~\ref{subsec:why-gpu}).
We use the terms \emph{embedding} and \emph{vector} interchangeably.

%\yxy{we need space to need to shrink. generally the writing can be more concise. For the paragraph below, maybe don't list the system names to save space. }
% how they are integrated into databases, explicit vs implicit
Relational databases store embeddings as a column, with either a dedicated \texttt{VECTOR} type~\cite{PgvectorRepo, SnowflakeVector, SQLServer2025Vector, MySQLHeatWaveVector} or an existing array type~\cite{DuckDBVSS, ClickHouseVSS, BigQueryVectorSearchFn, DatabricksNearestByJoinBlog26}.
An embedding model either runs outside the database and its output is loaded like any other attribute, or runs during query execution as a SQL function~\cite{SnowflakeAIEmbed, BigQueryGenerateEmbedding, HeatWaveMLEmbedRow, SQLServerAIGenerateEmbeddings, DatabricksAIQuery26, PgVectorizeRepo, DuckDBQuackformers}.
Either way, the embeddings reach the execution engine as a column of fixed-length vectors, and similarity computation becomes an ordinary relational operation.

\subsection{Vector Search}\label{subsec:vector-search}

%\yxy{both sections 2.2 and 2.3 can be shrunk aggressively. We need the background section to be at most 1.5 pages. Start with shrinking contents that are more tangential to our contributions.}

% what a vector search is, and how it is written in SQL
A vector search returns the top-$k$ nearest neighbors of one query vector from a dataset under a distance metric.
In SQL it is an ordering by distance with a limit.

% exact vs approximate search
An \textit{exact} search compares the query with every vector and returns the true neighbors, at a cost linear in the dataset size.
An approximate nearest neighbor (ANN) search trades some recall for speed by comparing only the candidates an index selects, most commonly from clusters (IVF~\cite{JegouPQ11}) or a proximity graph (HNSW~\cite{MalkovYashunin20}, CAGRA~\cite{OotomoCAGRA24}).

% integrated into relational databases, and the step from search to join
Relational databases add vector search through a vector type, distance functions, and an ANN index, so the optimizer can answer such a query with an index scan and compose it with filters and joins.
Stonebraker and Pavlo cite this integration as evidence that vector search is a feature of relational engines rather than a new architecture~\cite{StonebrakerPavloAround24}, and Zhang et al.\ find no inherent barrier to efficient vector search in PostgreSQL~\cite{ZhangPgLimits24}.
The syntax still varies, from \texttt{ORDER BY} with a limit~\cite{PgvectorRepo, DuckDBVSS, OracleAIVectorSearch} to a \texttt{VECTOR\_SEARCH} table function~\cite{BigQueryVectorSearchFn, SQLServerVectorSearchFn, DatabricksVectorSearchFn26}, and a vector extension is under way for the SQL standard~\cite{EisentrautSQL202y25}.
In all these systems the query side is one vector or a batch that a client submits; when it is instead a relation, stored or produced by other operators, the search becomes a similarity join.

\subsection{Similarity Join}\label{subsec:similarity-join}

%\yxy{Just want to double confirm: the definition below is "background", not what we propose in this paper? I guess this should be the case. }

% what a similarity join is & its three forms
Given a probe relation $R$ of $m$ vectors and a build relation $S$ of $n$ vectors, each of dimension $d$, and a distance function $\delta$, a similarity join returns the pairs $(r, s) \in R \times S$ that satisfy a similarity condition.
Prior work studies three forms of the condition, and we name our join modes after them:
\begin{itemize}
    \item \emph{kNN join}~\cite{BohmKrebsKNNJoin04} (\emph{per-row top-$k$}): for each $r \in R$, the $k$ rows of $S$ nearest to $r$; for example, batch retrieval and hard-negative mining~\cite{HuangFBRetrieval20, XiongANCE21}.
    \item \emph{$k$ closest pairs} or \emph{distance join}~\cite{HjaltasonSametDistJoin98, CorralClosestPair00} (\emph{global top-$k$}): the $k$ pairs in $R \times S$ with the smallest distance; for example, finding the city nearest to any river.
    \item \emph{$\varepsilon$-join}~\cite{ShimSimJoin97, KoudasSevcik98} (\emph{threshold}): every pair with $\delta(r, s) \le \varepsilon$; for example, semantic deduplication~\cite{AbbasSemDeDup23} and entity resolution~\cite{SantanaEMJoin25}.
\end{itemize}

% historical view, stages 1 and 2: algorithms, then database systems and clusters, all low-dimensional
Early work extended the spatial join~\cite{BrinkhoffSpatialJoin93} to feature vectors and avoided comparing every pair by partitioning or ordering the space~\cite{ShimSimJoin97, BohmEGO01, XiaGorder04}, and later work brought the join into database systems and clusters~\cite{ChaudhuriSSJoin06, ArasuDataCleaning11, SilvaSimJoinOp10, LuKNNMapReduce12, XieSimba16}.
This work targeted strings or data of at most ten dimensions; in high dimensions most pairs are roughly equally far apart, and such pruning weakens~\cite{BeyerNNMeaningful99}.

% learned embeddings and production SQL engines
Learned embeddings have renewed the join over high-dimensional vectors, and SQL engines are beginning to expose it directly.
BigQuery's \texttt{VECTOR\_SEARCH} accepts a whole table of queries~\cite{BigQueryVectorSearchFn}, and Spark adds a \texttt{NEAREST BY} clause for the per-row top-$k$ join, evaluated over the full cross product~\cite{ApacheSparkJIRA56395, SparkNearestByJoin26}.
Databricks runs the same clause with a fused GEMM operator, or with an IVF index built ahead of time for an approximate join~\cite{DatabricksNearestByJoinBlog26}.
DuckDB offers brute-force join macros~\cite{DuckDBVSS}, an HNSW index join~\cite{DuckDBVSSBlog24}, and recently \texttt{NEAREST BY}~\cite{DuckDBNearestByPR24137}.
Recent algorithms target approximate joins at this scale~\cite{XieSimJoin25, ChenDiskJoin25, KimVectorJoin26} (Section~\ref{sec:related}).

\subsection{GPU-Accelerated Data Processing}\label{subsec:gpu-data-processing}

% GPU SQL engines: analytics is bandwidth-bound, and GPU-native engines outperform CPU engines
Analytical queries scan large inputs and are typically bound by memory bandwidth, and a GPU offers several times the memory bandwidth of a CPU\@.
GPU SQL engines~\cite{HeavyDB, Kinetica, AramburuTheseus25, HeTQP22, Yogatama26} run analytical queries on the GPU.
Microsoft's TQP compiles SQL into tensor programs and runs queries up to 10$\times$ faster than specialized CPU and GPU systems~\cite{HeTQP22}, and Sirius shows that a GPU-native engine can outperform state-of-the-art CPU engines on TPC-H and ClickBench with higher cost efficiency~\cite{Yogatama26, SiriusClickBench25}.

% vector search and join on the GPU today
GPU vector search comes mainly from libraries that take a batch of queries per call: FAISS~\cite{JohnsonFaissGPU21} and NVIDIA cuVS~\cite{NvidiaCuVS26} with its graph index CAGRA~\cite{OotomoCAGRA24}, which FAISS now uses as its GPU backend~\cite{MetaFaissCuVS25}.
Research has extended GPU search to new indexes, larger-than-memory data, CPU--GPU cooperation, and ray-tracing cores~\cite{ZhaoSONG19, GrohGGNN22, KarthikBANG24, ZhangRummy24, TianFusionANNS25, LiuJuno24}, while commercial systems mostly build indexes on the GPU and search on the CPU~\cite{ElasticGPUIndexing, OpenSearchGPU25, SolrCuVS, OracleVectorIndexService}; Milvus~\cite{MilvusGPUIndex} and Kinetica~\cite{KineticaVectorSearch} also search on the GPU.
