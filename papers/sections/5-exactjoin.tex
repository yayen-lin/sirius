\section{Exact Vector Join}\label{sec:exact-join}

\yxy{no need to mention vector search to introduce exact vector join. Explain it as a block nested loop join.}
Exact vector search compares a query with every corpus row: it computes all the distances and then selects the nearest.
GPU libraries answer a join as a batch of such searches, and at the scale of a join almost all of that work is wasted, because the distances fill hundreds of gigabytes for an answer of a few hundred thousand pairs.
This section starts from that algorithm (Section~\ref{subsec:exact-algo}) and removes its waste in three steps: the join never writes a distance (Section~\ref{subsec:exact-kernel}), it filters with a bound that tightens as it scans (Section~\ref{subsec:exact-bound}), and it filters on 1- or 2-byte codes while still returning the exact answer (Section~\ref{subsec:exact-codes}).

\subsection{The Basic Algorithm}\label{subsec:exact-algo}

\yxy{this subsection should focus on explaining Figure 3. Especially the right part, since that's the key building block that the whole paper is built on top of. Also, don't repeat contents already discussed in previous sections.}

The exact join is a blocked nested-loop join over batches of the two inputs (Figure~\ref{fig:exact-join}, Section~\ref{subsec:reduction-modes}): each task joins one probe batch with one corpus batch, computes the distance of every pair (Step~1), and keeps the pairs the reduction asks for (Step~2).
Since $\lVert r-s\rVert^2=\lVert r\rVert^2+\lVert s\rVert^2-2\,r\cdot s$ and each row's norm is computed once, Step~1 needs the dot product of every probe row with every corpus row.
Laid out as a table with one row per probe row and one column per corpus row, these dot products are exactly the matrix product of the probe batch and the transposed corpus batch, so Step~1 is one GEMM per pair of batches, which tensor cores execute in hardware; cosine similarity is the same product over unit-length rows.

Run the way a search library runs it, Step~1 writes all $mn$ distances to GPU memory and Step~2 reads them back to keep $k$ per probe row; FAISS-GPU's flat search works this way, tile by tile.
For 10k probe rows and a 10M-row corpus, the distances fill 400\,GB in fp32 for an answer of 100k pairs.

\subsection{Filtering Inside the GEMM}\label{subsec:exact-kernel}

The first step removes that traffic: the join never writes a distance.
When a tile's dot products are complete, they are still in the registers of the threads that computed them.
Sirius's kernel compares each pair's distance there with a limit $L_r$ for the pair's probe row and appends only the pairs within it to a candidate buffer.
For a per-row top-$k$, $L_r$ is an upper bound on the probe row's $k$-th distance (Section~\ref{subsec:exact-bound}); for a threshold join it is $\varepsilon$.

Search kernels fuse the selection too: cuVS's \texttt{fusedL2Knn} keeps a running top-$k$ per query inside a CUDA-core kernel for $k\le64$~\cite{NvidiaCuVS26}, and flyKNNG selects the top-$k$ on tensor cores on the fly~\cite{JiFlyKNNG22}.
Both keep the selection's state inside the kernel, which fits one batch of queries searched in one pass.
A join needs more: every reduction, any $k$, a corpus that arrives in pieces from host memory or disk, and thousands of partitions joined one by one.
Sirius therefore moves the state out of the kernel.
The kernel only compares each distance with a number it is given, and the join decides what that number is.
This makes the kernel a stateless filter that every part of the join reuses: the exact join, each partition of the approximate join (Section~\ref{sec:technical-2:-approximate}), and corpus chunks streamed from host memory or disk (Section~\ref{sec:integration}).
It is also what lets the filter tighten its bound between calls (Section~\ref{subsec:exact-bound}) and run on lossy codes (Section~\ref{subsec:exact-codes}).
The kernel is otherwise a standard tensor-core GEMM: each thread block keeps one probe tile in the L2 cache, walks the corpus tiles, and copies the next tile's operands into shared memory while the current one is multiplied.

\subsection{A Bound That Tightens\yxy{needs better title}}\label{subsec:exact-bound}

\yxy{this subsection is more understandable, but still not easy to follow for a general reader. Try to improve clarity further.}
The filter helps only if its limit is close to the answer.
The ideal limit for a per-row top-$k$ is the distance to the probe row's true $k$-th neighbor, which is what the join is computing; a loose limit lets through almost every pair, and the join is back to writing distances.
Sirius therefore starts each probe row with a bound near the answer and tightens it as the corpus is scanned.

\paragraph{Seed}
Before the scan, each probe row's bound $b_r$ is set to its $k$-th smallest distance over a sample of corpus rows, taken from the whole corpus in the exact join and from the probe row's nearest partition in the approximate join (Section~\ref{subsec:approx-probe}).
The sample has 1\,024 rows or $8k$, whichever is more, so the seed stays near the answer as $k$ grows.
Any $k$ corpus rows give an upper bound on the $k$-th neighbor's distance, so the seed never excludes a row of the answer.

\paragraph{Lowering}
The corpus is scanned in pieces that double in size, so a corpus of $n$ rows takes $O(\log n)$ pieces.
After each piece, the pairs that passed are re-scored, merged into each probe row's running top-$k$, and the bound is lowered to the current $k$-th distance.
The first piece is sized so that the pairs passing it under the seed fit the candidate buffer; after a few pieces the bound is close to the final one, and each later piece passes about $k$ pairs per probe row.
Codes in host memory have no rows on the GPU to sample, so there the first piece runs without a bound and serves as the sample.

\paragraph{Other reductions}
A threshold join uses $\varepsilon$ as every row's bound and never lowers it.
A global top-$k$ runs the per-row search to depth $k$ and passes the per-row answers to the engine's top-$N$, since the $k$ nearest pairs overall are among the $k$ nearest of their probe rows.
A count over a threshold join is taken in the kernel itself (Section~\ref{subsec:integration-plan}).

\subsection{Exact Answers from Compact Codes}\label{subsec:exact-codes}

Once no distance is written, the multiplications are what remain, and they run in fp32 for every pair although almost every pair is discarded.
Tensor cores multiply narrow types much faster: on our GPU, fp16 at several times the fp32 rate and int8 at twice the fp16 rate.
Sirius therefore runs the filter on 1- or 2-byte codes of the rows instead of the fp32 rows.
A code distance only approximates the true one, so each row's limit is widened by the largest error the codes can introduce.
No pair of the exact answer is then filtered out, and the few extra pairs that pass are discarded when the survivors are re-scored in fp32, so the answer is the fp32 exact answer.

\paragraph{Codes}
The join builds the codes as its first step, inside the statement, as a hash join builds its hash table, and keeps them for later statements.
Probe rows are coded the same way when the join starts.
A float column is coded as fp16, one rounded value per component, or as int8.
For int8, each row is first multiplied by a random orthogonal matrix, generated once from a fixed seed, and each component $j$ of the rotated row is coded as $\mathrm{round}((x_j-o_j)/\gamma)$, clamped to $\pm127$, with an offset $o_j$ per component and one scale $\gamma$ per column.
The rotation preserves distances and spreads a component with a wide range over all components, so that one scale fits every component.
A column whose values are all integers from 0 to 255, such as SIFT, is converted to bytes without loss: its distances on the int8 tensor cores are exact, so its limit needs no widening and its survivors no re-scoring.

\paragraph{The limit}
When the codes are built, Sirius records each row's coding error $e_x=\lVert x-\hat x\rVert$, where $\hat x$ is the decoded code, the largest error of the column, $e=\max_x e_x$, and each probe row's own error $e_r$.
A pair within the bound, $\lVert r-s\rVert\le\sqrt{b_r}$, then has $\lVert\hat r-\hat s\rVert\le\sqrt{b_r}+e_r+e$ by the triangle inequality, so the filter keeps every such pair with the limit
\[
    L_r=\bigl(\sqrt{b_r}+e_r+e\bigr)^2 .
\]
For fp16 the tensor cores accumulate the products in fp32, so the limit also adds the worst-case rounding of a $d$-term fp32 sum, $2d\,2^{-24}(\lVert\hat r\rVert+\max_s\lVert\hat s\rVert)^2$, from the standard forward-error bound of a dot product~\cite{Higham02}.

RaBitQ also rotates vectors, quantizes them and uses an error bound to decide which candidates to re-rank~\cite{GaoRaBitQ24}, but its bound holds with high probability, which suits approximate search.
Ours is deterministic, because it is computed from each row's measured error, so no row of the answer is lost.
FaSTED computes Euclidean distances on fp16 tensor cores and accepts a small loss of accuracy~\cite{CurlessFaSTED25}; we use the same arithmetic as a filter and recover the exact distances by re-scoring.

The two float codes trade speed against robustness.
int8 halves the bytes of fp16 and doubles the tensor-core rate, but one scale per column makes its error grow with the widest component, so on skewed data the limit widens and many pairs pass.
fp16 keeps an exponent per value, tolerates skew, and is the default for float columns; int8 is an option (Section~\ref{subsec:eval-ablations}).
