\section{Exact Vector Join}\label{sec:exact-join}

The exact vector join is a blocked nested-loop join: it compares every probe row with every build row and keeps the pairs the reduction asks for.
Section~\ref{subsec:exact-algo} shows where a straightforward implementation of the join of Section~\ref{sec:vector-join-execution} spends its time.
The rest of the section describes the three design decisions that remove that cost without giving up exactness: the selection runs inside the GEMM (Section~\ref{subsec:exact-kernel}), its bound is seeded and tightened as the scan proceeds (Section~\ref{subsec:exact-bound}), and the GEMM runs on 1- and 2-byte codes whose error the bound absorbs (Section~\ref{subsec:exact-codes}).
%The join compares each distance with a per-row limit while the distance is still in registers and writes only the pairs within the limit (Section~\ref{subsec:exact-kernel}); it starts each row's limit near its final value and tightens it as the scan proceeds (Section~\ref{subsec:exact-bound}); and it computes the distances it compares from 1- or 2-byte codes, widening the limit by the codes' known error so that the fp32 answer is unchanged (Section~\ref{subsec:exact-codes}).

\subsection{GEMM-Based Exact Join}\label{subsec:exact-algo}

For two vectors $r$ and $s$, their inner product is $r \cdot s$, cosine similarity divides it by $\lVert r \rVert \lVert s \rVert$, and squared L2 distance expands to $\lVert r \rVert^2 + \lVert s \rVert^2 - 2\, (r \cdot s)$, so each of these metrics needs only the dot product of the pair and the norm of each vector.
If the probe vectors are stacked as the rows of an $m \times d$ matrix $R$ and the build vectors as the rows of an $n \times d$ matrix $S$, all $mn$ dot products are the entries of the matrix product $RS^\top$.
The norms take $O((m+n)d)$ work and are computed once per vector, while the product takes $O(mnd)$ and is computed once per pair, so the work is dominated by GEMM.

Sirius implements the exact vector join as a blocked nested-loop join.
Each task multiplies a batch of probe vectors $R_i$ by the transposed
batch of build vectors $S_j^\top$, computing pairwise distances using
GEMM (Figure~\ref{fig:exact-join}). The kernel processes the resulting
scores in $128\times128$ tiles, with up to $T$ tasks executing
concurrently.

A straightforward implementation materializes all $mn$ scores before
performing the local reduction. This creates substantial memory traffic:
for 10k probe rows and a 10M-row build side, the intermediate FP32
scores occupy 400\,GB, even when the result contains only 100k pairs.
As Figure~\ref{fig:exact-ablation} shows, this overhead can dominate
the computation. Sirius therefore fuses distance filtering into GEMM,
discarding irrelevant pairs before their scores are written to memory.
The following subsections describe how Sirius makes this filtering
effective while preserving exact results.


\subsection{Distance Bounding Inside the GEMM}\label{subsec:exact-kernel}

Sirius fuses distance computation and candidate filtering in one GPU
kernel. Each probe row $r$ has a filtering limit $L_r$. For per-row
top-$k$, the limit is derived from an upper bound $b_r$ on the
row's $k$-th nearest-neighbor distance. For threshold joins, the limit
is determined by the user-specified threshold $\varepsilon$. When
compact codes are used, $L_r$ also accounts for their encoding error
(Section~\ref{subsec:exact-codes}).

After computing each tile's scores, the kernel compares them against
the corresponding limits while the scores are still available in
registers. Only passing candidates are written to GPU memory, as
(row ID, build ID, score) triples; discarded scores are never
materialized. After a group of kernel launches, Sirius merges the
candidates into the running top-$k$ results. The updated results tighten subsequent
filtering limits (Section~\ref{subsec:exact-bound}).

The three join modes differ in their filtering and reduction semantics.
Per-row top-$k$ maintains a separate bound for each probe row. Global
top-$k$ obtains up to $k$ candidates per probe row and then applies
the engine's global top-$k$ reduction. A threshold join uses a fixed
limit and returns every pair satisfying the threshold.



\subsection{Progressive Bound Tightening}\label{subsec:exact-bound}

A loose filtering limit can admit too many candidates, making
filtering more expensive than materializing the scores
(Section~\ref{subsec:eval-ablations}). Sirius therefore initializes
each probe row with a valid upper bound and tightens it as better
neighbors are found. This optimization applies to per-row and global
top-$k$; threshold joins instead use their fixed threshold.

\paragraph{Seeding.}
Before the main scan, Sirius evaluates each probe row against a sample
of build vectors and sets $b_r$ to the sample's $k$-th nearest-neighbor
distance. Because the sample is a subset of the build relation, this
distance is an upper bound on the true $k$-th nearest-neighbor distance.
Thus, the seed affects pruning efficiency but not correctness.

The implementation samples the first 1,024 build rows, or $8k$ rows
for larger $k$. In the approximate join, the seed is obtained from the
probe row's nearest partition (Section~\ref{subsec:approx-join}).

\paragraph{Tightening.}
Sirius scans the build relation in sequential batches, grouping batches
into progressively larger pieces subject to the working-memory limit.
After each piece, it merges the newly verified candidates into the
running top-$k$ and lowers $b_r$ to the current $k$-th nearest distance.
Geometric growth in piece size limits the number of bound updates to
$O(\log n)$ over a scan of $n$ build rows.

A tight seed helps keep the candidate buffer small. Under a representative
sample of 1,024 rows, approximately $k$ candidates per probe row are
expected to pass the initial bound. Subsequent tightening reduces this
number further.

\subsection{Exact Answers from Compact Codes}\label{subsec:exact-codes}

After fusing filtering with GEMM, distance computation remains a major
cost. Sirius reduces this cost by using the lower-precision formats
supported efficiently by GPU tensor cores. On the evaluated GPU, FP16
provides higher throughput than TF32, and INT8 provides further gains.
Sirius computes approximate scores using compact codes, filters
candidates using conservative error bounds, and re-scores surviving
candidates in FP32. This avoids materializing scores for pairs that
cannot affect the exact result.

\paragraph{Codes.}
Sirius converts floating-point vectors to FP16 or INT8. FP16 rounds
each component to its representable value. INT8 uses a shared scale
$\gamma$ and component-specific offsets $o_j$:
\[
    \hat{x}_j =
    \operatorname{round}\left(\frac{x_j-o_j}{\gamma}\right),
\]
with values clamped to $[-127,127]$. To mitigate coordinate skew,
the INT8 path first applies a fixed random orthogonal transformation,
which preserves Euclidean distances while distributing component
magnitudes more evenly.

Native byte-valued data, such as SIFT vectors, can instead be shifted
by $-128$ to use INT8 tensor cores without lossy quantization.

\paragraph{Error-bounded filtering.}
For each vector $x$, Sirius records its encoding error
$e_x=\|x-\hat{x}\|$, where $\hat{x}$ is the decoded representation.
Let $e=\max_{s\in S} e_s$ be the maximum build-side error and $e_r$
the error for probe row $r$. By the triangle inequality, any pair
satisfying $\|r-s\|\leq\sqrt{b_r}$ must also satisfy
\[
    \|\hat{r}-\hat{s}\|
    \leq \sqrt{b_r}+e_r+e.
\]
Consequently, a conservative filtering limit on squared Euclidean
distance is
\[
    L_r = \left(\sqrt{b_r}+e_r+e\right)^2.
\]
The widened limit admits every pair that could satisfy the original
bound. It may also admit false positives, which are eliminated by
rescoring the candidates in FP32.

FP16 tensor-core computations accumulate in FP32 but still incur
floating-point rounding error. Sirius therefore accounts for an
additional forward-error tolerance of
\[
    \eta_{\mathrm{fp32}} =
    2d\,2^{-24}
    \left(\|\hat{r}\|+\max_{s\in S}\|\hat{s}\|\right)^2
\]
following the standard error analysis~\cite{Higham02}.
