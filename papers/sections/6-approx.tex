\section{Approximate Vector Join}\label{sec:technical-2:-approximate}\label{sec:approx-join}

The exact vector join, as a block nested loop join, must compute every vector pair in the inputs, so its cost grows with $N^2$.
Relational engines face the same problem with large inputs, and they answer it with join algorithms that never compare most pairs.
Table~\ref{tab:join-analogy} lists the classic algorithms next to their vector counterparts.

An index library answers a join as an index nested-loop join, which pays off, as for relational data, when the index already exists and the probe side is small.
Modern OLAP warehouses and lakehouses rarely rely on such indexes, since a join often runs on intermediate results over which no index can be prebuilt; we follow the same observation and build the approximate join as a co-partitioned hash join.
Our approximate join is instead a partitioned hash join in the manner of GRACE~\cite{KitsuregawaGrace83}: it partitions both inputs at query time by one function, k-means over the build side, and joins each build partition with the probe rows that fall into it (Figure~\ref{fig:hash-vs-approx}).
It departs from a hash join in one place.
A probe row falls into its $n_p$ nearest partitions rather than one, because its nearest neighbors can lie just across a partition boundary.

\input{hash-vs-approx}

Figure~\ref{fig:hash-vs-approx} shows the idea.
A hash join partitions both inputs by a hash of the key and joins each pair of matching partitions.
The vector join has no key, so it partitions by k-means: it clusters the build side into $N$ partitions, each around a \emph{centroid}, and sends each probe row to the partitions whose centroids are nearest.
Each partition is small enough to join on the GPU in one task, so the join becomes $N$ small exact joins, and a probe row's nearest neighbors are found unless they lie in a partition it does not visit.
The three subsections follow the three steps: partitioning the build side, routing the probe side, and joining partition by partition.

\subsection{Partitioning the Build Table through K-means}\label{subsec:approx-build}

Sirius partitions the build side inside the statement that needs the partitions, as a hash join builds its table.
It samples 256 rows per centroid, or fewer when that sample does not fit beside what the GPU already holds, and fits cuVS's balanced k-means, the one its IVF indexes use~\cite{NvidiaCuVS26}.
The k-means is balanced because a partition is the unit of work below, and a few oversized partitions would leave most of the GPU idle.
Sirius then assigns every build row to its nearest centroid.
This assignment is a per-row top-1 join of the build side with the centroids, which Sirius runs with the bounded kernel of Section~\ref{subsec:exact-kernel}.
Finally it writes the build side in partition order, one contiguous run per partition, coded as in Section~\ref{subsec:exact-codes}, with a map back to the row ids.
The partitions stay in the session for later statements.

The number of partitions $N$ trades build time for join time: the fit and the assignment grow with $N$, and the join's work per probe row, $n_p$ partitions of $n/N$ rows each, falls with it.
Sirius picks $N$ with a cost model that prices the build (k-means fit, assignment, writing the partitions) and the join (bytes read and multiply-adds performed, at rates measured once per GPU) for DuckDB's estimate of the probe rows, over the candidates $N_{\mathrm{ref}}=\lfloor\sqrt{n}\rfloor$, at most 1\,024, and its doublings up to $16N_{\mathrm{ref}}$ with at least 256 rows per partition (Section~\ref{subsec:integration-plan}).
A plain-SQL join is exact by default; a user asks for an approximate answer with \texttt{SET vector\_join\_probes = }$n_p$, as with pgvector's \texttt{ivfflat.probes}.
The user's $n_p$ is read at $N_{\mathrm{ref}}$ partitions: at $N$ partitions the join probes $n_p\sqrt{N/N_{\mathrm{ref}}}$, because recall follows $n_p/\sqrt{N}$ empirically, and on Deep10M one setting keeps recall@10 between 0.956 and 0.964 for every count from 256 to 16\,384.

\subsection{Probe: Co-Partitioning the Probe Side}\label{subsec:approx-probe}

The probe side is partitioned by the same centroids.
Finding each probe row's $n_p$ nearest centroids is itself a small vector join, of $m$ probe rows with $N$ centroids; Sirius runs it as one GEMM and a per-row top-$n_p$, though any method that finds a row's nearest centroids would do.
Sorting the resulting (probe row, partition) pairs by partition gives one \emph{slice} per partition: the partition and every probe row routed to it, with each probe row appearing in $n_p$ slices.
A row of the answer is missed only when its partition is not among those its probe row visits.
So $n_p$ trades recall for time, and $n_p=N$ returns the exact answer.

\subsection{Join: Each Partition Once}\label{subsec:approx-join}

After co-partitioning, the join is $N$ independent small joins, one per slice, and any vector join algorithm could run them.
Sirius runs each slice as an exact join with the kernel of Section~\ref{sec:exact-join}, so the codes and the bound lose nothing and the answer equals the exact join restricted to the probed partitions: routing is the only approximation, and every reduction of Section~\ref{sec:vector-join-execution} carries over.

Joining partition by partition, rather than probe row by probe row as an index search does, is what makes the join cheap at large probe sides: a partition is read once per probe block and multiplied in one GEMM with every probe row routed to it, so with 10k probe rows, 256 partitions and $n_p=8$ each read serves about 300 probe rows, where a search reads the partition once per probe row (FAISS's \texttt{big\_batch\_search} walks an IVF index in this order for the same reason~\cite{DouzeFaiss24}).
The bound of Section~\ref{subsec:exact-bound} also carries across the small joins: a first sweep joins each probe row with its nearest partition only, and the $k$-th distance found there seeds the row's bound for its other $n_p-1$ slices, which lower it further as they finish.
Slices too small to pay for a kernel launch of their own are launched together.
