% define vector join and its three modes
A \emph{vector join} is a similarity join between two relations of embeddings that runs inside a SQL engine, and we use this term for the rest of the paper.
Its three forms vary by their reduction \emph{modes}: per-row top-$k$, global top-$k$, and threshold.

\input{quadrant}

% Figure 1, relational side: OLTP and OLAP are different problems with different engines
Relational workloads split into transaction processing (OLTP), which looks up rows through persistent indexes and is measured by latency, and analytical processing (OLAP), which joins whole tables through structures built at query time and is measured by throughput~\cite{StonebrakerOneSize05, StonebrakerPavloAround24}.
We argue that vector data is now at the same transition point (Figure~\ref{fig:quadrant}).

% Figure 1, vector side: vector search is the OLTP half, and the vector join is the OLAP half
Vector search is the OLTP half: it asks ``what is similar to this'' and returns the nearest neighbors of one query vector.
The vector join is the OLAP half: it asks ``what is similar to what'' and relates the rows of one table of vectors to the rows of another.
A relational join follows relationships that were declared ahead of time as keys, while a vector join finds relationships that nobody declared, between rows that share no key but a meaning.

\subsection{Why the GPU}\label{subsec:why-gpu}

%\yxy{we can use quantitative metrics to show how compute intensive vector join is and how GPU and tensor cores are so much better than CPU for this type of computation. This section also should be much shorter. We can keep figure 2.}
% how compute-intensive the vector join is
A vector join is far more compute-intensive than a relational join.
Comparing two vectors takes one multiply-accumulate (MAC) per dimension, and an exact join compares every pair, so joining $m$ probe rows with $n$ corpus rows of $d$ dimensions takes $mnd$ MACs.
For 10K probe rows and 10M corpus rows of 128 dimensions, that is about $10^{13}$ MACs.

% the vector join is a matrix product, so its work is dominated by GEMM
This work is a dense matrix multiplication (GEMM).
For two vectors $r$ and $s$, their inner product is $r \cdot s$, cosine similarity divides it by $\lVert r \rVert \lVert s \rVert$, and squared L2 distance expands to $\lVert r \rVert^2 + \lVert s \rVert^2 - 2\, (r \cdot s)$, so every metric needs only the dot product of the pair and the norm of each vector.
If the probe vectors are stacked as the rows of an $m \times d$ matrix $R$ and the corpus vectors as the rows of an $n \times d$ matrix $S$, all $mn$ dot products are the entries of the matrix product $RS^\top$.
The norms take $O((m+n)d)$ work and are computed once per vector, while the product takes $O(mnd)$ and is computed once per pair, so the work is dominated by GEMM, which the tensor cores of our GPU execute at \andy{X}~TFLOPS, against \andy{Y}~TFLOPS for \andy{CPU}.

\input{exact-probe-sweep}

% a search is bandwidth-bound and a join is compute-bound, as Figure 2 shows
A single search ($m=1$) is a matrix-vector product that uses each corpus vector once and is bound by memory bandwidth, while a join reuses each corpus vector across all probe rows and becomes compute-bound as the probe side grows.
Figure~\ref{fig:exact-probe-sweep} shows this shift on an exact threshold join against SIFT10M\@.
Sirius is only 3.6$\times$ faster than DuckDB at $m=1$ but 106$\times$ faster at $m=10$K, because its throughput keeps rising with $m$ while DuckDB's levels off by $m=100$.

\subsection{Vector Join Interface}\label{subsec:vector-join-interface}

%\yxy{try to be more concise. }

\input{vector-join-modes}

% two interfaces, both support the three modes
Sirius exposes the vector join through two interfaces, a table function and native SQL, and both support all three modes (Table~\ref{tab:vector-join-api}).
The table function gives more control over how the join executes, most importantly the choice of approximate search, while native SQL runs the queries that users already write for DuckDB without changes.

% explaining TVF
\input{vector-join-tvf}

The table function, \texttt{sirius\_knn\_join} (Table~\ref{tab:tvf-signature}), takes the probe relation $R$ as its left input and the corpus relation $S$ as its right input, each given as a table and a vector column.
The remaining arguments are optional and passed by name.
The join mode follows from the arguments: the join returns the per-row top-$k$ by default, \texttt{eps} selects threshold, and \texttt{join\_mode=>\sq{global}} selects global top-$k$.
\texttt{metric} chooses L2 or cosine distance.
\texttt{search\_mode} chooses how the join is computed: \texttt{\sq{exact-gemm}} computes distances with GEMM, \texttt{\sq{exact}} computes them directly without GEMM, and \texttt{\sq{approx}} runs the approximate join (Section~\ref{sec:approx-join}).

% explaining native SQL syntax
Native SQL recognizes the vector join in queries that DuckDB already accepts.
A \texttt{LATERAL} subquery that orders the corpus by distance to each probe row and keeps the first $k$ rows is a per-row top-$k$ join.
A cross product of the two tables ordered by distance with a \texttt{LIMIT} of $k$ is a global top-$k$ join.
A join whose predicate bounds the distance by $\varepsilon$ is a threshold join.
The distance function sets the metric: \texttt{array\_distance} for L2 and \texttt{array\_cosine\_distance} for cosine.
Native queries always run the exact join.
Requesting approximate search from SQL needs new syntax, and the \texttt{NEAREST BY} clause that Spark and DuckDB have recently added (Section~\ref{subsec:similarity-join}) is a natural starting point, which we leave to future work.

% join algorithms and their vector counterparts; we focus on two
A relational join can run as a nested-loop join, a block nested-loop join, an index nested-loop join, or a hash join, and a vector join has a counterpart for each; Table~\ref{tab:join-analogy} lists the main ones.
We focus on two of them.
The exact join is a block nested-loop join: it compares every probe row with every corpus row, which works on small inputs but does not scale to large ones (Section~\ref{sec:exact-join}).
The approximate join is a partitioned hash join: it co-partitions both inputs and compares rows only within matching partitions, which scales to much larger inputs (Section~\ref{sec:approx-join}).

\input{exact-join}

% the three modes share the distance computation and differ only in the reduction
In the exact join, all three modes compute the distance between every probe row and every corpus row, and they differ only in the reduction applied to the resulting $mn$ pairs.
Per-row keeps $k$ pairs for each probe row, global keeps $k$ pairs overall, and threshold keeps every pair within $\varepsilon$.
Sirius cannot apply this reduction to all $mn$ pairs at once because by its design it partitions both relations into batches during the scan.
So Sirius computes one pair of a probe batch and a corpus batch at a time and the reduction therefore has two levels: a local reduction within each batch pair, and a global reduction that combines local results into the final answer (Figure~\ref{fig:exact-join}).
In every mode, Sirius gathers output columns only for pairs that survive the local reduction and never for the full set of pairs.

\paragraph{Per-row}
Per-row returns the $k$ nearest corpus rows for each probe row.
Within a batch pair, the local reduction keeps a list of $k$ nearest neighbors in that corpus batch for each probe row.
The global reduction then merges, for each probe row, one list of $k$ candidates per corpus batch into the final $k$.
With $q$ corpus batches, the merge reads at most $mkq$ candidates instead of $mn$ pairs, and the output has exactly $k$ rows per probe row, or $n$ rows when the corpus has fewer than $k$.

\paragraph{Global}
Global returns the $k$ nearest pairs across the whole join.
Within a batch pair, the local reduction runs the per-row step and keeps the $k$ nearest pairs in that batch pair.
The global reduction is then an ordinary relational top-$N$ over at most $k$ candidates per batch pair.
Sirius runs this step with the engine's existing top-$N$ operators.

\paragraph{Threshold}
Threshold returns every pair whose distance falls within a radius $\varepsilon$.
Within a batch pair, the local reduction keeps every pair within $\varepsilon$.
Whether a pair survives depends only on its own distance, so the global reduction is the union of the local results.
The output size ranges from zero to $mn$ and depends on the data and on $\varepsilon$.
