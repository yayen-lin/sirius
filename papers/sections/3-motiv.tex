\subsection{The Transition: From Similarity Search to Similarity Join}\label{subsec:the-transition}

\input{quadrant}

% argument 1: vector data is now at the same transition point
% the shift from OLTP to OLAP and the questions they answer, and that leads us to the vector OLAP
Relational workloads split into transaction processing (OLTP) and analytical processing (OLAP) because the two turned out to be different problems~\cite{StonebrakerPavloAround24}.
An OLTP query asks ``what matches this'': it looks up one customer, one order, or one account, and returns in milliseconds.
An OLAP query asks ``what matches what'': it joins whole tables against each other and aggregates the result, as in total sales by region over the last quarter.
OLTP serves lookups from persistent indexes built ahead of time (e.g., B-trees) and is measured by latency, while OLAP scans its inputs and builds temporary structures (e.g., a hash table) at query time over intermediate results, and is measured by throughput.
Stonebraker and \c{C}etintemel argued that these differences end the era of a single general-purpose engine, and that specialized engines outperform row stores designed for OLTP on analytical workloads~\cite{StonebrakerOneSize05}.
Column stores such as C-Store and MonetDB proved this in practice and analytical processing grew into its own execution model and field of study~\cite{StonebrakerCStore05, IdreosMonetDB12, StonebrakerPavloAround24}.
These engines now form the basis of decision support and analysis of historical data that organizations use to guide business decisions~\cite{ChaudhuriDayal97}.
We argue that vector data is now at the same transition point (Figure~\ref{fig:quadrant}).

% the quadrant, and the introduction of vector OLAP + what it brings
Similarity search is the OLTP half: it asks ``what is similar to this'' and returns the nearest neighbors of one query vector.
The similarity join is the OLAP half: it asks ``what is similar to what'' and relates the rows of one table of vectors to the rows of another.
The similarity join introduces a new kind of relation.
A relational join follows relationships that were declared ahead of time as keys, while a similarity join finds relationships that nobody declared, and between rows that share no key but a meaning.
Recent trends in hardware and storage make this relation practical to compute.
Columnar engines store a column of embeddings as one contiguous matrix, and the GPU is built to compare one matrix against another (Section~\ref{subsec:why-gpu-database}).
Just as column stores made it feasible to ask new questions of structured data, the GPU and columnar storage together make it feasible to relate unstructured data at the scale of whole collections.
Relational OLAP became the basis of decision support over structured data, and we believe vector OLAP can play the same role for everything that embeddings make comparable.

% the use cases in vector join that strengthen the transition and the shortcomings that set up the next subsection
The workloads for the similarity join already exist under different names.
In machine learning pipelines, semantic deduplication joins a training corpus against itself to find and remove near-duplicate data points, and pruning this redundancy has been shown to improve both data efficiency and downstream model quality~\cite{HuSieveIVF26, AbbasSemDeDup23}.
In data integration, entity resolution matches records across two sources by the similarity of their learned embeddings, which reduces a classically hard matching problem to a similarity join~\cite{SantanaEMJoin25, SantanaRibeiro23}.
In retrieval and recommendation, a batch of user or query embeddings is compared against an item catalog or document corpus at once for offline candidate generation, evaluation, or the mining of hard negatives that train the next embedding model~\cite{HuangFBRetrieval20, XiongANCE21, ThakurBEIR21}.
More generally, a batched similarity search is itself a join, and GPU libraries design their search APIs around it (Section~\ref{subsec:vector-search}).
However, the two halves are not equally developed.
The OLTP half is now a standard feature and offered by nearly every major database.
The OLAP half, in contrast, has reached SQL engines only recently, and to our knowledge it runs on the CPU (Section~\ref{subsec:vector-join}).
Where an engine has no similarity join, users write it as one search per probe row, which is a nested-loop join, a plan that optimizers typically avoid when the probe side is large.

\subsection{The Similarity Join as a GPU Database Operator}\label{subsec:why-gpu-database}

% argument 2: similarity join on a GPU engine
% the three stages, and the industry has completed the first two
Relational analytics reached its current form in three stages.
It was first expressed in SQL, then it became physical operators, and finally engines were redesigned around the hardware that runs these operators.
The similarity join has completed the first two stages.
BigQuery, DuckDB, Spark, and Databricks already expose it in SQL, and DuckDB and Databricks execute it with dedicated physical operators (Section~\ref{subsec:vector-join}).
What remains is the third stage, and the analysis behind the Databricks operator indicates where it leads.
Computing distances one pair at a time reads two values for every multiply-accumulate (MAC), so it is bound by memory bandwidth. \andy{explains MACs = distance computations × d in evaluation}
To make the join compute-bound, the Databricks operator reuses each corpus vector across a tile of probe rows, and their roofline estimate shows that this holds once about 64 query vectors are buffered~\cite{DatabricksNearestByJoinBlog26}.
Once the join is compute-bound, its speed depends on how much arithmetic the hardware delivers.
We argue that the third stage is to run the similarity join as an operator in a GPU-native SQL engine.

% why the GPU is a good fit
If the similarity join is the analytical half of vector processing, it should run where analytical processing is heading.
Analytical queries scan large inputs and are typically bound by memory bandwidth, and a GPU offers several times the memory bandwidth of a CPU\@.
Yogatama et al.\ show that a GPU-native SQL engine outperforms state-of-the-art CPU engines on TPC-H and ClickBench, with higher cost efficiency~\cite{Yogatama26, SiriusClickBench25}.
The similarity join is an especially good fit, because moving from one query vector to many changes the kind of work the hardware does.
Under the common metrics, distance computation reduces to dot products and vector norms (Section~\ref{subsec:embeddings-and-vectors}).
For two vectors $r$ and $s$, their inner product is $r \cdot s$, cosine similarity divides it by $\lVert r \rVert \lVert s \rVert$, and squared L2 distance expands to $\lVert r \rVert^2 + \lVert s \rVert^2 - 2\, r \cdot s$.
If the probe vectors are stacked as the rows of an $m \times d$ matrix $R$ and the corpus vectors as the rows of an $n \times d$ matrix $S$, all $mn$ dot products are the entries of the matrix product $RS^\top$.
The norms take $O((m+n)d)$ work and are computed once per vector, while the product takes $O(mnd)$ and is computed once per pair, so when both sides are large, the work is dominated by a dense matrix multiplication (GEMM).
A single search ($m=1$) is a matrix-vector product, in which each corpus vector is read once and used once, so it is bound by memory bandwidth and leaves most of the GPU's compute idle.
For a join, $RS^\top$ is a matrix-matrix product in which each corpus vector is reused across many probe rows, so the work becomes compute-bound and runs as GEMM.
