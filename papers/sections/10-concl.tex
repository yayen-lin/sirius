\section{Conclusion}\label{sec:conclusion}

Vector search answers one query vector at a time.
A vector join relates two tables of vectors, and we argued that it should be built like a relational join: at query time, on the GPU, and planned by the optimizer.
Sirius's exact join is a blocked nested-loop join on tensor cores that filters 1- and 2-byte codes under a deterministic bound and re-scores the survivors in fp32.
Its approximate join is a hash join whose hash function is k-means, and it joins each partition once with the exact join's kernel.
Both run through the engine's memory tiers, from plain SQL.
With every build charged, the approximate join is faster than every GPU index we measured at every recall target from 0.90, and at 10k probe rows the exact join is 5.9--7.8$\times$ faster than FAISS-GPU's exact search, up to 100M rows.
When an index already exists, an index nested-loop join over it can be the cheaper plan, as in relational engines; choosing between the two from the catalog is the planner's next decision.
