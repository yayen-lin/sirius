    \begin{abstract}
        Vectors are becoming a standard data type in databases. Besides vector search, a growing class of workloads require \textit{joining} two columns of vectors within a query, such as semantic deduplication, entity resolution, and offline recommendation. % all ask which pairs of rows are close.
        We call this operation a \emph{vector join}.
        It resembles a relational join but is far more compute-intensive due to performing hundreds of multiply-adds per vector pair.
%and a join compares every pair, so it is far more compute-intensive than any relational join.
        We observe that this computation pattern fits perfectly on a GPU: %Our insight is that this work fits the GPU:
        a many-to-many vector comparison is a dense matrix multiplication, which tensor cores are optimized for in native hardware speed. %, and a join reuses each vector across many rows where a search reads it once.
        We present a GPU-optimized vector join operator, its exact and approximate variants, and integrate it into Sirius, a GPU-native analytics engine. %that the query optimizer plans like a relational join.
        Our exact vector join is a blocked nested-loop join that filters inside the tensor-core GEMM under a deterministic bound over 1- and 2-byte codes; our approximate vector join is a partitioned hash join whose partitioning function is k-means.
        We show that %, with every build charged,
        the exact vector join is 6--7$\times$ faster than the second-fastest GPU system, FAISS-GPU's exact search, on 1M to 100M rows, and the approximate vector join beats the best of five GPU indexes by 4--6$\times$ at 10M probe rows, at recall 0.95 and above.
        When running vector joins within a query, Sirius on GPU shows speedups from 48$\times$ to 10\,000$\times$ over DuckDB on CPU.
    \end{abstract}
